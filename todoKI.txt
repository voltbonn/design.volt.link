# todoKI.txt - Roadmap zur Vollendung von design.volt.link

Diese Liste ist in sinnvoller Abarbeitungsreihenfolge sortiert. Ziel ist zuerst ein sauberes, oeffentliches Version-1-Designportal ohne Login und ohne oeffentlichen Storybook-Eindruck. Danach folgen redaktionelle Vollendung, technische Haertung, Deployment und spaeter Version 2 mit Login/Vorlagenbereich.

## 1. Projektziel und Informationsarchitektur final klaeren

1. Festlegen, was Version 1 genau ist:
   - Oeffentliche React/Vite-Website unter design.volt.link.
   - Kein Login.
   - Kein oeffentlicher Vorlagenbereich.
   - Storybook nur als interne Arbeits- und Darstellungsumgebung fuer Komponenten und Designinhalte.

2. Festlegen, was Version 1 nicht zeigt:
   - Keine Planungskapitel in der oeffentlichen Navigation.
   - Keine anpassbaren Vorlagen.
   - Keine Login-, Admin- oder Backend-Hinweise als Hauptinhalt.
   - Keine oeffentliche Storybook-URL als sichtbarer Navigationspunkt.

3. Navigationsstruktur finalisieren:
   - Einstieg
   - Grundlagendesign
   - Digitale Anwendung
   - Anwendungen
   - Hilfe
   - Archiv
   - Impressum und Datenschutz immer unten.

4. Entscheiden, ob "Archiv" oeffentlich sichtbar bleiben soll oder nur als Hilfsseite fuer alte Designs dient.

5. Entscheiden, welche Sprache die primaere Redaktionssprache ist. Aktuell ist Deutsch die faktische Quelle.

## 2. README und Projektbeschreibung korrigieren

1. README an den aktuellen Stand anpassen:
   - Link zu anpassbaren Vorlagen aus der Beschreibung der oeffentlichen Oberflaeche entfernen.
   - Storybook klar als interne Arbeitsumgebung beschreiben.
   - Build-Ziel fuer die oeffentliche Seite als `npm run build` und Output `dist/` dokumentieren.
   - Storybook-Build separat als technische Pruefung dokumentieren.

2. Alte Storybook-Formulierungen entfernen oder korrigieren:
   - Keine Aussage mehr, dass Storybook die oeffentliche Seite ist.
   - Keine Deployment-Anleitung mehr, die `storybook-static` als Hauptoutput beschreibt.

3. README-Abschnitt "Naechste Schritte" durch Verweis auf `todoKI.txt` ersetzen oder beide TODO-Dateien zusammenfuehren.

4. Entscheiden, ob `todo.txt` bleibt oder in `todoKI.txt` aufgeht. Wenn `todo.txt` bleibt, nur sehr kurze aktuelle Bugs dort fuehren.

## 3. Oeffentliche Oberflaeche stabilisieren

1. Header finalisieren:
   - Keine Vorlagen- oder Storybook-Links.
   - Nur sinnvolle Werkzeuge: Raster, Hintergrund, Konturen, Sprache, Theme.
   - Auf kleinen Viewports pruefen, dass Buttons nicht umbrechen oder ueberlaufen.

2. Sidebar fertigstellen:
   - Ausklappbare Gruppen beibehalten.
   - Normales Seitenscrolling sicherstellen, wenn viele Gruppen aufgeklappt sind.
   - Aktive Seite beim Laden automatisch sichtbar halten.
   - Suche so pruefen, dass sie auch in eingeklappten Gruppen Treffer sichtbar macht.
   - Entscheidung treffen, ob Gruppenstatus in `localStorage` gespeichert werden soll.

3. Mobile Layout pruefen:
   - Sidebar, Suche und Gruppen auf Smartphone-Breite testen.
   - Sicherstellen, dass Impressum/Datenschutz erreichbar bleiben.
   - Topbar-Werkzeuge so ordnen, dass sie nicht zu viel vertikalen Raum verbrauchen.

4. Content-Header pruefen:
   - Abschnitt und Seitentitel sollen auf mobilen Viewports nicht abgeschnitten wirken.
   - Lange Titel muessen sauber umbrechen oder ellipsieren.

5. Ansichtswerkzeuge pruefen:
   - Raster muss alle relevanten Flaechen erfassen.
   - Konturmodus darf Inhalt nicht unlesbar machen.
   - Hintergrundwechsel muss fuer alle Kapitel visuell funktionieren.

## 4. Theme- und Sprachwechsel reparieren

1. Bug aus `todo.txt` beheben:
   - Von Deutsch auf andere Sprache und zurueck wechseln muss stabil funktionieren.
   - Alle sichtbaren Seiten- und UI-Texte muessen nach Sprachwechsel aktualisieren.

2. Theme-Bug aus `todo.txt` beheben:
   - Wechsel von Light zu Dark und zurueck muss stabil funktionieren.
   - Gespeichertes Theme aus `localStorage` muss beim Laden korrekt angewendet werden.

3. Overlay-/Werkzeug-Zustaende pruefen:
   - Raster, Kontur und Hintergrund muessen im Dark Mode lesbar bleiben.
   - Falls ein Overlay existiert oder spaeter wieder kommt: Texte und Controls muessen mehrsprachig sein.

4. i18n-Struktur aufraeumen:
   - UI-Labels in `src/design/i18n.jsx` halten.
   - Inhaltsseiten in `src/design/content/guidePages.js` halten.
   - Keine hart codierten sichtbaren Texte in Komponenten, ausser es sind Produktnamen oder technische Werte.

5. Jede neue oder geaenderte UI-Beschriftung in `de`, `en`, `nl`, `fr` pflegen.

## 5. Alte Storybook-Beispielinhalte entfernen

1. Standard-Storybook-Beispiele pruefen:
   - `stories/Button.jsx`
   - `stories/Button.stories.js`
   - `stories/Header.jsx`
   - `stories/Header.stories.js`
   - `stories/Page.jsx`
   - `stories/Page.stories.js`
   - zugehoerige Beispiel-CSS und Assets.

2. Entscheiden:
   - Entweder komplett entfernen.
   - Oder durch echte Volt-Komponenten-Stories ersetzen.

3. Storybook-Assets aufraeumen:
   - Nicht benoetigte Default-Bilder und Icons entfernen.
   - Nur Assets behalten, die fuer echte Komponenten-Dokumentation gebraucht werden.

4. Storybook-Struktur vereinheitlichen:
   - Nur Storys und MDX-Dateien fuer echte Designsystem-Komponenten und interne Pruefung.
   - Keine Storybook-Seiten als Ersatz fuer die oeffentliche Website.

## 14. Tests und technische Pruefung einrichten

1. Build muss immer laufen:
   - `npm run build`

2. Storybook-Build als technische Pruefung laufen lassen:
   - `npm run build-storybook`
   - Nur wenn Storybook-Inhalte gepflegt sind.

3. Vitest-Konfiguration pruefen:
   - Gibt es sinnvolle Unit- oder Component-Tests?
   - Falls nicht: minimale Tests fuer kritische Logik ergaenzen.

4. Playwright-Smoketests ergaenzen:
   - Startseite laedt.
   - Sprache kann gewechselt werden.
   - Theme kann gewechselt werden.
   - Sidebar-Gruppen lassen sich ein-/ausklappen.
   - Suche liefert Treffer.
   - Keine oeffentlichen Links zu `/storybook/`, `#templates` oder Planungsseiten.

5. Accessibility-Checks ergaenzen:
   - Storybook a11y Addon nutzen.
   - Optional Playwright/Axe fuer die oeffentliche Seite.
